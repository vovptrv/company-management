# 🏢 Company Management

A full-stack module for managing **companies**, their **employees** and their **projects**.
A Django REST API with JWT authentication is paired with a React SPA, and the whole stack —
PostgreSQL, Django under gunicorn, and the frontend behind nginx — comes up with a single
`docker compose up` on port **8080**.

Anyone can browse the data. Only an authenticated user can create, edit or delete it —
the frontend hides every write control until you log in, and the API answers `401` to
anonymous writes regardless.

---

## ✨ Features

- 🔐 **JWT Authentication** — access/refresh tokens, transparent refresh on the frontend
- 👁️ **Read for everyone, write for members** — `IsAuthenticatedOrReadOnly` across all resources
- 🏢 **Three related resources** — companies → employees, companies → projects, employees ↔ projects
- 🧩 **Project membership as a sub-resource** — add/remove an employee with a single `POST`/`DELETE`
- ✅ **Business validation** — cross-company assignments, project date ranges and case-insensitive
  uniqueness are rejected with field-level errors
- 🔍 **Filtering, search, ordering and pagination** — on every list endpoint
- 📚 **OpenAPI documentation** — Swagger and ReDoc generated by `drf-spectacular`
- 🌱 **Seeder** — fills the database with realistic demo data and a demo user
- 🧪 **Tests** — permissions, CRUD, validation, membership, cascades and auth
- 🐳 **Dockerized** — three services, one port, no manual steps after `up`

## 🚀 Quick Start

**1. Create the `.env` file** from the template and fill in the values:

```bash
cp .env.example .env
```

**2. Bring the stack up:**

```bash
docker compose up --build
```

The first start builds both images, waits for PostgreSQL, applies migrations, collects static
files and seeds the database. Then open **http://localhost:8080**.

**3. Log in** with the seeded account — the create / edit / delete controls appear across the app:

| Email | Password |
|---|---|
| `user@example.com` | `demo12345` |

The demo user is deliberately **not** staff. For the Django admin, create a superuser:

```bash
docker compose exec backend python manage.py createsuperuser
```

## 🗃️ Data Model

```
Company ──< Employee >──< Project >── Company
```

**Company** — `name`, `description`, `industry` (choices), `email`, `website`
**Employee** — `company` (FK), `first_name`, `last_name`, `email`, `position`, `hire_date`
**Project** — `company` (FK), `employees` (M2M), `name`, `description`, `status` (choices),
`start_date`, `end_date`

All three inherit `created_at` / `updated_at` from an abstract `TimeStampedModel`.

Enforced in the database, not only in the serializers:

- company names are unique, case-insensitively
- employee emails are unique, case-insensitively
- a project name is unique **within its company**, case-insensitively
- `end_date` may not precede `start_date`, and may not exist without one

Deleting a company deletes its employees and its projects. Deleting a project leaves its employees
in the company — only the membership rows disappear.

## ⚙️ API Reference

Every write (`POST`, `PUT`, `PATCH`, `DELETE`) requires an `Authorization: Bearer <access>`
header. Reads never do. Lists are paginated:
`{ "count": 80, "next": "...?page=2", "previous": null, "results": [ ... ] }`.

### 🔑 Authentication

| Endpoint | Description |
|---|---|
| `POST /api/auth/token/` | `{ "email": "...", "password": "..." }` → `{ "access", "refresh" }`. Login is by **email**. |
| `POST /api/auth/token/refresh/` | `{ "refresh": "..." }` → a new access token |
| `GET /api/auth/me/` | the current user; the frontend uses it to decide whether to render write controls |

Access tokens live 60 minutes, refresh tokens 1 day. `GET /api/auth/me/` answers with the user
record, which is what the SPA keeps in its auth context:

```json
{ "id": 1, "email": "user@example.com", "username": "demo", "is_staff": false }
```

### 📚 Resources

| Endpoint | Filters | Search | Ordering |
|---|---|---|---|
| `/api/companies/` | `industry` | `name` | `name`, `created_at` |
| `/api/employees/` | `company` | first name, last name, email | `last_name`, `created_at` |
| `/api/projects/` | `company`, `status` | `name` | `name`, `created_at` |

Each supports the full `GET` / `POST` / `GET {id}` / `PATCH {id}` / `DELETE {id}` set, plus
`page` and `page_size`. Example: `GET /api/projects/?company=3&status=active&ordering=name`.

A company is flat — every field it has is returned in both the list and the detail view:

```json
{
  "id": 3,
  "name": "Bradley-Hoffman",
  "description": "Reactive multi-tasking hub",
  "industry": "technology",
  "email": "contact@bradley-hoffman.com",
  "website": "https://bradley-hoffman.com/",
  "created_at": "2026-09-23T09:12:44.113Z",
  "updated_at": "2026-09-23T09:12:44.113Z"
}
```

Employees and projects carry relations, and there the detail views return richer objects than the
lists: an employee's `projects` and a project's `employees` are plain ids in a list response and
expanded objects in a detail one. A table that only shows a count does not need to download every
related record, while a detail page gets everything it renders in a single request.

```json
{
  "id": 17,
  "company": 3,
  "company_name": "Bradley-Hoffman",
  "projects": [5, 9],
  "first_name": "Diana",
  "last_name": "Meyer",
  "email": "diana.meyer@example.com",
  "position": "Data scientist",
  "hire_date": "2023-04-11",
  "created_at": "2026-09-23T09:12:44.402Z",
  "updated_at": "2026-09-23T09:12:44.402Z"
}
```

`GET /api/employees/17/` returns the same object with `projects` expanded:

```json
{
  "projects": [{ "id": 5, "name": "Synergized client-server hub", "status": "active" }]
}
```

A project in its detail shape:

```json
{
  "id": 5,
  "company": 3,
  "company_name": "Bradley-Hoffman",
  "employees": [
    { "id": 17, "first_name": "Diana", "last_name": "Meyer", "position": "Data scientist" }
  ],
  "name": "Synergized client-server hub",
  "description": "Roll out the new analytics pipeline.",
  "status": "active",
  "start_date": "2025-02-01",
  "end_date": null,
  "created_at": "2026-09-23T09:12:44.771Z",
  "updated_at": "2026-09-23T09:12:44.771Z"
}
```

**Validation rules**, all returned as field errors:

- a company name, an employee email or a project name within its company may not repeat, in any case
- a project's `end_date` may not precede `start_date`, nor exist without one
- every project member must belong to the project's company
- an employee cannot be moved to another company while on planned or active projects
- a completed project keeps members who have since moved elsewhere; they are re-checked only when
  the project is reopened or moved

### 🔗 Project Membership

| Endpoint | Description |
|---|---|
| `POST /api/projects/{id}/employees/{employee_id}/` | adds one employee; adding twice is a no-op, an employee from another company is rejected |
| `DELETE /api/projects/{id}/employees/{employee_id}/` | removes the membership; the employee stays in the company |

Both return the updated project in the detail shape above.

## 🖥️ Frontend

A React SPA served as static files by nginx.

| Route | Page |
|---|---|
| `/companies` | list + industry filter + search |
| `/companies/:id` | details, its employees and its projects |
| `/employees` | list + company filter + search |
| `/employees/:id` | profile and project memberships |
| `/projects` | list + company/status filters + search |
| `/projects/:id` | details and an editable team table |
| `/login` | email + password |

- **Server-driven lists.** Search, filters and the page number live in the query string, so the
  back button and a copied URL restore the exact view. Nothing is filtered client-side.
- **Write controls follow the session.** Buttons and dialogs render only when `/api/auth/me/`
  returns a user; the API enforces the same rule independently.
- **Cache invalidation.** Every mutation invalidates the affected TanStack Query resources, so
  related views — a company's project list, an employee's memberships — refresh themselves.
- **Field-level errors.** DRF's error payloads are mapped back onto the inputs that caused them.

## 🌱 Seeding & Tests

The seeder runs on container start and **skips itself if companies already exist**, so restarting
never duplicates data. Each company gets 3–8 employees and 1–4 projects, with members drawn from
its own staff and dates consistent with the project status — a planned project has no start date
in the past, a completed one has both dates. Everything happens inside one transaction, and the
demo user is created alongside the data.

```bash
docker compose exec backend python manage.py seed --companies 30   # more data
docker compose exec backend python manage.py seed --flush          # wipe first, then reseed
docker compose exec backend python manage.py test                  # run the test suite
```

The test runner creates and drops its own database, so seeded data is untouched. The suite covers
permissions (anonymous reads pass, anonymous writes get `401`), CRUD for all three resources,
every validation rule, membership add/remove, cascade deletes and the auth endpoints.

## 📁 Project Structure

```
company-management/
├── backend/
│   ├── config/                 # settings, root urls, pagination
│   ├── companies/
│   │   ├── models.py           # Company, Employee, Project + DB constraints
│   │   ├── serializers.py      # list/detail serializers + business validation
│   │   ├── views.py            # three ModelViewSets + membership actions
│   │   ├── tests.py
│   │   └── management/commands/seed.py
│   ├── users/                  # email-based user model, JWT + /me endpoints
│   ├── Dockerfile
│   ├── entrypoint.sh           # migrate → collectstatic → seed → gunicorn
│   └── requirements.txt
├── frontend/
│   ├── src/
│   │   ├── api/                # axios client, per-resource queries, types
│   │   ├── auth/               # AuthContext
│   │   ├── components/         # dialogs, tables, shared UI
│   │   ├── hooks/              # useListParams, useCrudDialogs
│   │   └── pages/
│   ├── Dockerfile              # node build → nginx
│   └── nginx.conf              # SPA fallback + reverse proxy
├── docker-compose.yml
└── .env.example
```

The backend is split in two apps: `users` owns authentication and the email-based user model,
`companies` owns the domain. `migrate`, `collectstatic` and `seed` live in `entrypoint.sh` rather
than the Dockerfile, so a `docker compose up` against an existing volume still applies new
migrations; all three are idempotent.
